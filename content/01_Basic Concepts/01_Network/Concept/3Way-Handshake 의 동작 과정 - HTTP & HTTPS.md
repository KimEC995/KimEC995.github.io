# 3 Way Handshake의 동작 과정 - HTTP

[[TCP]]는 연결을 확립하기 전 **3Way Handshake**라는 [[HandShaking]]을 진행한 후, 응답이 잘 수신되면 그 때 연결을 확립한다. **이 때문에 TCP는 연결 지향형 프로토콜이 되었다.**

어떤 과정인지 살펴보자. 참고로 대부분 [[WireShark]]로 모니터링 하지만, [[TCP의 상태]]를 전부 다 모니터링 하는건 좀 번거로워서 플래그 값과 이론으로 유추할 것이다.

---
## 0. 환경
![[3-Way-동작(1).png]]

우선 클라이언트와 서버가 있다. 이 둘은 [[TCP]]를 통해 송수신할 예정이며 [[포트 번호|포트]]는 80번을 사용한다.

클라이언트는 아무런 동작도 없는 상태여서  [[TCP의 상태#CLOSED|CLOSED]] / 서버는 열어두어서 [[TCP의 상태#LISTEN|LISTEN]] 이다.

#### 실제 환경 - 클라이언트
- OS: Kali Linux
- IP: 192.168.10.250

#### 실제 환경 - 서버
- OS: Rocky Linux
- Service Name: httpd
- F/W: 80 Open
- IP: 192.168.10.50

```
[root@localhost ~]# netstat -nat | grep :80
tcp6       0      0 :::80                   :::*                    LISTEN 
```

## 1. 접근 시도
![[3-Way-동작(2).png]]

클라이언트가 서버에게 [[TCP 제어 플래그#SYN|SYN]] 플래그를 전송했다.

![[3-Way-동작(3).png]]

이 때 [[TCP 헤더]]를 보면

![[3-Way-동작(4).png]]

플래그는 `SYN`만 활성화, 다른 플래그는 비활성화 되어있다.

그리고 [[TCP 헤더#시퀀스 번호(32 Bit)|시퀀스 번호]]의 절대 번호는 `1960397160`이고, 상대 번호는 `0`이다.

---
## 2. 서버 응답
![[3-Way-동작(5).png]]

서버는 클라이언트에게 [[TCP 제어 플래그#SYN|SYN]] + [[TCP 제어 플래그#ACK|ACK]] 플래그를 보낸 후, 상태는 [[TCP의 상태#SYN-RECEIVED|SYN-RECEIVED]]로 변경되었다.

![[3-Way-동작(6).png]]

![[3-Way-동작(7).png]]

이 때 시퀀스의 값은 서버에서 보낸건 처음이기 때문에 상대 번호는 `0` / 절대 번호는 다른 값이지만, ACK 번호가 `접근 시도의 시퀀스 번호 + 1`이 된 것을 볼 수 있다. 

---
## 3. 클라이언트 응답(연결 확립)
![[3-Way-동작(8).png]]

클라이언트가 서버에게 ACK를 보내고 서로 [[TCP의 상태#ESTABLISHED|ESTABLISHED]]가 된 걸 알 수 있다.

![[3-Way-동작(9).png]]

![[3-Way-동작(10).png]]

이 때 클라이언트가 보내는 시퀀스 번호와 ACK 번호가 위 과정과 반대되고 `+1`된 모습을 확인할 수 있다.

# HTTPS의 변화

위에서 [[TCP의 상태#ESTABLISHED|ESTABLISHED]]되고 바로 데이터 송수신을 시작하면 HTTP이고, 이후 [[TLS 프로토콜|TLS]]를 이용한 HTTPS는 [[암호화와 복호화|암호화]] 과정을 더 수행한 후 `ESTABLISHED`한다.
